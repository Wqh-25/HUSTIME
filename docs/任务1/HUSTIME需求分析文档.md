## 1 背景、问题与分析依据

### 1.1 背景与核心问题

大学生可能同时从课程群、班级群和活动群接收作业、报名、考试、会议等通知。聊天内容与通知混杂，任务时间也可能用“明天”“下周五”等相对表达，或在后续通知中改期、取消。用户需要把这些信息整理为自己的待办与日历，并能回看原通知，避免错记日期、重复登记或误取消任务。

本项目的问题假设来自提出者在选题讨论中表达的需求，不是已经完成的校园调查结论。尚未获得真实学生总体的漏记比例、每人群数量分布或节省时间统计，不使用虚构调研数字证明需求。20个账号、5人并发等数值是课程原型的容量目标，不是调查样本或市场规模。

### 1.2 产品目标与价值边界

HUSTIME应完成“已授权来源接入/文本导入—通知信息提取—候选核对—个人日程维护—站内提醒”闭环。价值集中在减少重复抄录、显式暴露不确定时间、维护改期与取消的一致性，以及保留来源。

“自动捕捉”指自动生成候选，不能解释为未经用户确认就派发个人任务或修改日历。系统不替用户决定是否选修课程、参加活动或执行他人任务，不声称消除所有漏记。

### 1.3 采集与理解必须分开

QQ消息接入获取获准接收的文本，大模型API理解已经获取的文本。大模型API本身不提供访问用户QQ群历史的权限。关闭模型时，接入、有限规则提取、手动录入、候选确认和日历仍应可用。

用户已反馈实际测试NapCatQQ能接收指定群实时消息并读取群历史。该反馈支持备选接入的初步可行性，但NapCatQQ基于NTQQ/OneBot路线，与既有设计的腾讯官方QQ Bot路线不同。本次用户明确选择：首版保持实时接收，历史获取列为待评估扩展；不据此悄悄替换接入方案。核实范围见附件HV-01。

## 2 目标用户、角色与运行条件

### 2.1 角色与使用需求

| 角色 | 主要需求 | 权限边界 |
| --- | --- | --- |
| 访问者 | 理解产品用途、登录方式和数据处理范围 | 无法查看群消息、候选和个人日程 |
| 个人用户USER | 接入本人已获准使用的群来源，核对候选，管理自己的任务/活动及提醒 | 只读写本人数据；不能通过资源ID访问其他人内容 |
| 接入维护者OPS | 配置授权群、查看连接与故障、暂停异常接入 | 仅运维信息；无个人正文或日历访问入口 |
| QQ群管理者 | 在QQ侧同意机器人入群并设置实际允许的接收能力 | 外部参与者，不是HUSTIME中的团队任务管理员 |

账号由维护者配置，不开放匿名注册。USER与OPS为互斥角色；维护者需要个人日程时使用独立USER账号。身份验证与群管理者对采集的授权是两件事：用户能够在群中完成挑战，不等于群已同意接入。

### 2.2 环境与前提

首版为可从浏览器访问的单实例Web应用，部署目标为2 vCPU、4 GiB内存、SSD，时间解释规则为Asia/Shanghai。容量目标为20个个人账号、5个同时在线用户、每用户最多5个有效群订阅、500条ACTIVE个人条目；每天最多20,000个去重后按用户展开的文本处理单元。同一群消息被2名用户订阅计2个单元，平台重投不重复计单元，但其入口次数须单独报告。推导与峰值适用条件见7.3，不以日总量代替突发吞吐保证。

实际接入要求：官方机器人账号与凭证可用、机器人已进入授权白名单群、目标群与账号实际支持全量接收。未满足时必须显示“受限/未开通”，不可用有心跳、仅@消息或模拟导入冒充真实全群监控。

云模型需部署方凭证、网络与余额，并由用户开启MODEL_AUTO。模式关闭、凭证未配置、预算用尽或模型故障时采用有限规则。默认RULE_ONLY。浏览器关闭时站内通知仍可生成，但不保证设备离线弹窗。

| ID | 假设/风险 | 依据与处理 |
| --- | --- | --- |
| AS-01 | 本项目账号能开通目标群全量事件 | 官方存在该事件，账号权限尚需真实联调；为上线阻断前提 |
| AS-02 | 部分通知可用明确词语与时间识别 | 用户需求及规则组件支持；覆盖范围限于第5章，不承诺理解全部聊天 |

| AS-04 | 用户愿意核对候选 | 这是控制错误的产品取舍；5人定性试用用于发现操作障碍，不能推断学生总体接受率 |

## 3 应用范围与系统边界

### 3.1 首版范围

首版包括：登录及个人数据隔离、已授权QQ群实时文本接入、文本导入、模型/规则双模式提取、多事项候选审阅、个人任务与固定活动、改期/取消确认、个人周日历、站内提醒、调用额度、来源追溯、内容清理和脱敏运维。

### 3.2 明确排除

不包含小组任务分配、任务依赖/关键路径、团队绩效、自动最优排期、微信群自动采集、OCR、语音转写、任意群历史完整拉取、QQ撤回自动取消任务、短信/邮件/手机离线推送、第三方日历双向同步。

QQ历史接口存在性不改变首版范围。模型提取出DDL也不意味着知道任务执行耗时，系统不自动把截止时刻画成一段执行时间。

### 3.3 低优先级远期候选

| 候选 | 优先级 | 本次状态与原因 |
| --- | --- | --- |
| FUT-01 群历史导入/补采 | 低 | 用户明确列为待评估扩展；先验证历史跨度、完整性、版本及授权，不能用于掩盖首版断线遗漏 |
| FUT-02 单向日历文件导出 | 低 | 可能方便迁移，但未由用户确认纳入首版；另立需求后再实现 |

这两项不计入当前18项FR或首版验收。当前基线自身也有低优先级范围：FR-02的别名编辑、FR-13的周日历视图、FR-15的增强检索、NFR-07的操作速度优化，见第10章；隐私和错误取消防护仍为高优先级。

## 5 业务规则与时间语义

| 规则ID | 无二义性约定 |
| --- | --- |
| BR-01 | 群来源按外部群ID识别，群名只作别名。同名群不同，改名不改变订阅身份。 |
| BR-02 | 每条源消息可生成0..10条独立候选；超过10条明确提示分拆，不静默截取。每条候选可独立确认或拒绝。 |
| BR-03 | sent_at是原发送时间，received_at是接收时间，二者分开。相对日期以sent_at和Asia/Shanghai解释。 |
| BR-04 | sent_at未知时只自动解析完整年月日或带时区绝对时刻；省略年份、星期或相对日期不以当前时间补足。 |
| BR-05 | 月日无歧义时依据原发送年份并展示该依据；跨年含混优先保留未知，不能因日期在过去就推到下一年。 |
| BR-06 | TASK有due_date或due_at，二者互斥，也可经用户显式确认保持未知；TASK没有start_at/end_at。 |
| BR-07 | EVENT必须有带时区start_at、end_at且start_at<end_at；不使用DDL替代活动开始时间。 |
| BR-08 | 日期型截止不自动变成23:59。用户日期提醒默认09:00，仅是提醒偏好，不是事实DDL。 |
| BR-09 | 本周/下周按ISO星期一为一周开始；单独“周五”“晚上12点”“周日之前”等未消歧表达保留疑点。 |
| BR-10 | CREATE/UPDATE/CANCEL均为候选动作。确认时相关性必须RELEVANT，UNKNOWN/IRRELEVANT须先由用户修正；拒绝不写日程。 |
| BR-11 | 改期/取消必须由用户选择本人条目并基于最新内容确认。条目已被他处修改时拒绝覆盖并要求刷新。标题或DDL相似仅作提示，不自动合并或覆写。 |
| BR-12 | 完成COMPLETED仅适用于TASK；取消CANCELLED表示不再要求执行；删除移除个人记录并停止提醒，语义不同。 |
| BR-13 | 平台重投在90天窗口内不重复提取；相似通知不等于重复源消息。超过90天的旧QQ事件不自动提取。 |
| BR-14 | 固定活动按半开区间[start,end)判断冲突；10:00结束与10:00开始不冲突。仅提示，不自动移动。 |
| BR-15 | 全量、仅@、导入三类来源状态须可区分；导入不证明群实时接入已通过。 |
| BR-16 | 所有个人资源按当前登录用户隔离；模型返回的身份或资源标识不能赋予权限。 |

### 5.1 规则模式明确支持范围

规则可对“提交、上交、截止、报名、缴费、需完成”等任务词和“考试、会议、集合”等活动词进行筛选，并结合明确日期/时刻生成候选。时间支持完整年月日、无歧义月日、今天/明天/后天、本周/下周＋星期、HH:mm、明确上午/下午与点钟半点。

按换行、编号、分号分句后分别配对事项和日期；同一句多事项无法配对时保留待人工处理。明确“无需提交”等否定表达不能当作新任务。跨消息“上次那个”“和刚才一样”等指代、图片、语音和含混时刻不承诺自动解释。关键词匹配是筛选环节，不能替代时间归一化、否定识别、本人相关性和改期目标判断。

## 6 功能需求

“应”表示本基线的规范性要求；下列验收点直接给出输入条件与可观察结果，可独立判定。TC编号只作详细用例索引，定义见[关联设计13.2](../HUSTIME软件设计文档.md#132-关键用例与检查点)，不代替本节判定。高/中/低对应P0/P1/P2；若同一编号含不同优先级，明确到验收点，不降低其中的安全约束。频率为场景推断而非实测数据，排序依据见第10章。

### 6.1 FR-01 登录与个人资源隔离

**优先级：高。来源：SRC-U02、SRC-U04、SRC-D01。** 所有个人操作的前提是USER登录。输入为账号凭证、会话及资源ID；输出为本人数据或明确错误。OPS只能访问运维功能，不能借角色访问个人正文。退出后会话应失效，身份与资源归属在服务端验证。

- AC-01：未登录访问个人资源须先登录；两个USER交换消息、候选、订阅、日程及通知标识读写，均不能查看或改变对方内容；提示不得泄露该资源是否属于他人。
- AC-02：以OPS账号直接尝试个人读写操作均被拒绝；退出后原登录状态不能继续访问。验证方法：双账号交叉操作、退出后重试与角色测试，关联TC-29、TC-30。

### 6.2 FR-02 已授权群订阅

**优先级：高（绑定与控制）；低（别名编辑）。来源：SRC-U02、SRC-T01、SRC-D01、SRC-U06。** 仅允许绑定已获授权白名单群。输入为一次性验证挑战及可信群事件；输出为个人订阅、群别名、接收模式和状态。挑战有效5分钟且只消费一次；每用户最多5个有效订阅。暂停/解除不删除已确认个人条目。

- AC-01（高）：有效挑战仅绑定当前用户与对应群；向非白名单群发送、过期后提交或重复使用挑战均不能绑定。同名但群标识不同不得串用。
- AC-02（高）：暂停或解除后不再产生新提取；已有个人条目仍可查看；仅@能力明确标LIMITED。重新验证后可恢复订阅。关联TC-01、TC-02、TC-06。
- AC-03（低）：用户可修改本人群来源显示别名；修改后历史条目仍关联同一群，不改变授权、接收模式或其他人的别名。以两个同名群分别改别名检查不串用；对应HMI-02、设计UI-02。

### 6.3 FR-03 实时文本接收与去重

**优先级：高。来源：SRC-U02、SRC-T01、SRC-D01。** 前提是实际QQ接入能力通过验证。输入为官方群文本事件；输出为带外部消息/群标识、原发送时间、接收时间的来源记录和处理状态。消息可重复、延迟或中断，系统不得假定恰好一次投递。

- AC-01：获准测试群中的普通文本和@文本在全量模式均被接收；仅@模式不得通过全量验收；无授权来源不进入提取。
- AC-02：同源事件在90天窗口重投100次，每用户仅一份来源及一次提取；不同用户各自可见且相互隔离。超过90天旧QQ事件标STALE，不自动提取。关联TC-01、TC-03、TC-04、TC-05、TC-28。
- AC-03：断线状态、最近接收时间和观察到的间隙可见；无法恢复时不伪造或宣称已补齐历史。

### 6.4 FR-04 文本导入与时间基准

**优先级：高。来源：SRC-U02、SRC-T03、SRC-D01。** 输入为1..4,000 Unicode字符文本、来源标签和可选sent_at；输出为可定位的来源记录及可查询处理状态。导入入口是独立能力，不替代真实接入验收。

- AC-01：一次导入提交因双击或网络重试重复发送时，只生成一份来源与提取结果；用户主动再次导入作为新操作区分。4,001字符须明确提示超长且不截断；排队、完成无事项、失败及已清理状态能区分。
- AC-02：原发送10月16日、10月20日导入的“明天18:00交报告”应指10月17日；sent_at=null时相对日期不落定，完整年月日仍可处理。关联TC-07/08/14。

### 6.5 FR-05 模型结构化提取

**优先级：高。来源：SRC-U02、SRC-T02、SRC-D01。** MODEL_AUTO开启、来源有效、配置和额度可用时，系统可发送当前通知及必要时间/本人命中标志给模型。输出0..10条候选，包含动作、类型、标题、时间、原文证据、相关性和疑点。模型不得取得日程写入或外部执行权限。

- AC-01：多事项通知生成可独立核对的候选；证据可在当前原文定位；不上传完整群历史、OpenID清单或他人日程。
- AC-02：空输出、截断、非法枚举、超过10项、伪证据和非法日期被拒收，不写日程；模型JSON合法也须过业务校验。关联TC-09/12/13/35。

只发送当前通知减少无关聊天上传和费用，也使“上次那个改到明天”缺少目标上下文。此类通知允许生成目标未知的改期候选，由用户选择本人条目；无法确定事项时标待人工处理。明确写出事项和新日期的独立改期仍可提取。该取舍降低跨消息自动化覆盖率，不降低错改防护；质量集必须保留缺上下文样例并按7.1计分。

### 6.6 FR-06 无模型提取与故障回退

**优先级：高。来源：SRC-U02、SRC-T02、SRC-T03、SRC-D01。** RULE_ONLY不发模型请求；MODEL_AUTO遇到未配置、关闭、无额度、认证/余额、限流、超时、无效输出或等待执行机会超过规定上限时转有限规则并记录原因。零候选可为成功处理结果。等待与完成时限见7.2。

- AC-01：拦截网络统计，RULE_ONLY处理100条支持范围文本时模型请求为0；输出候选遵循相同确认契约。
- AC-02：故障替身分别注入模型错误，均有明确原因及规则/人工入口，不用空列表掩盖处理状态；一条通知不会因为回退同时产生两套有效候选。关联TC-10/11/12/16/35。

### 6.7 FR-07 时间类型、精度与疑点

**优先级：高。来源：SRC-U02、SRC-T03、SRC-D01。** 输入为通知时间表达与原发送时间，输出为日期、带偏移时刻、活动区间或null与疑点。系统应遵守BR-03至BR-09，不擅自增加精度。

- AC-01：TASK的due_date/due_at互斥，无执行区间；EVENT的start_at<end_at。非法日期、无偏移时刻、反向活动区间不得确认。
- AC-02：日期型截止不变成23:59；未知TASK由用户显式确认待安排且无时间提醒；缺结束时间的EVENT须补全。关联TC-07/08/15/17。

### 6.8 FR-08 本人相关性

**优先级：高。来源：SRC-U01、SRC-U02、SRC-D01。** 候选相关性为RELEVANT/IRRELEVANT/UNKNOWN。可靠@目标可提供建议，无可靠标识或课程参与依据时使用UNKNOWN；昵称相同不能证明身份。

- AC-01：明确@本人/@他人样例得到相应建议或保守UNKNOWN，未明确分配的通知不自动变为本人任务。
- AC-02：UNKNOWN/IRRELEVANT时尝试确认必须被拒绝并说明需判断相关性，日程保持不变；用户修正为RELEVANT后才允许继续确认。关联TC-09、TC-17、TC-29。

### 6.9 FR-09 候选审阅与人工确认

**优先级：高。来源：SRC-U02、SRC-U04、SRC-D01。** 用户应能查看原文证据、提取方式、时间基准和疑点，编辑、确认或拒绝候选。无论哪种模式，未确认不得修改个人日程。

- AC-01：有n个候选时逐项处理互不影响；拒绝不生成条目。补全缺失项后可确认；不提供首版一键全部确认或自动批量取消。
- AC-02：输入非法日期、制造同时修改冲突或打开已过期候选时，应保留用户草稿、定位问题并说明补全/刷新/重新导入条件；已过期候选不能确认。关联TC-17、TC-18、TC-20、TC-28、TC-36。

### 6.10 FR-10 重复确认与变更一致性

**优先级：高。来源：SRC-U04、SRC-D01。** 同一候选只能确认一次；成功后条目、来源、变更记录与提醒应一致可查。基于旧内容的操作不得覆盖他处已提交的新结果；失败时不得留下部分完成的业务结果。

- AC-01：对同一候选重复确认100次，只有一个对应条目及一组有效提醒；重试原操作可查看既有结果；把重试内容改成不同内容须提示冲突而不能悄悄重执行。
- AC-02：两个窗口基于同一旧内容同时提交不同修改，只接受其中一次，另一次要求刷新；模拟保存中断后重新打开，结果应为完整旧状态或完整新状态，无孤立提醒。关联TC-18、TC-20、TC-23、TC-31。

### 6.11 FR-11 个人条目管理

**优先级：高。来源：SRC-U01、SRC-U02、SRC-D01。** 用户可手动新增、编辑、完成、恢复、取消和删除本人TASK/EVENT；输出更新后的条目及操作结果。最多500条ACTIVE个人条目，超限明确报错。

- AC-01：TASK可完成/恢复，EVENT不能标COMPLETED；恢复ACTIVE同样检查500条上限；无关用户无法操作。
- AC-02：删除后原条目不可恢复，未来及该条目历史站内提醒清除；其他条目和共有来源不误删。关联TC-21/22/29。

### 6.12 FR-12 改期与取消维护

**优先级：高。来源：SRC-U01、SRC-U02、SRC-D01。** 改期/取消通知只能生成UPDATE/CANCEL候选。系统提示最多5个本人目标，用户明确选择后确认；输出修改结果或取消状态，并保留可查看的初始与变更来源。

- AC-01：同名不同课程任务不自动覆盖；目标不确定时不执行；QQ原消息撤回不自动取消个人条目。
- AC-02：改期/取消成功后旧提醒不再触发，条目详情可查看前后值及来源；两窗口竞争时旧内容不能覆盖新内容，要求刷新重审。关联TC-19、TC-20、TC-22、TC-23。

### 6.13 FR-13 日程视图与冲突提示

**优先级：中（列表与冲突）；低（周日历视图）。来源：SRC-U01、SRC-U02、SRC-D01、SRC-U06。** 用户应能从任务列表查看个人活动、DDL、日期型/未知时间任务及状态；输出重叠提示但不自动移动。周日历作为便于比较时间的增强视图，可在基本列表之后实现。FR-11的条目详情和FR-14的提醒不依赖周日历。

- AC-01（中）：列表应区分EVENT起止、TASK截止日期/时刻和待安排，显示状态；新增相邻活动不提示冲突，新增重叠活动给出提示但不自动移动。以10:00结束/10:00开始及重叠15分钟两组输入检查。
- AC-02（低）：周日历正确切周及筛选；EVENT显示占用块，TASK显示截止标记，未知任务单列；不能把DDL伪装执行区间。单次日期查询跨度≤93天。关联TC-15、TC-21、TC-36。

### 6.14 FR-14 站内提醒

**优先级：高。来源：SRC-U01、SRC-D01。** 输入为确认时间及用户偏好，每个有效提醒触发最多生成一条持久化站内通知，条目可安排多个提醒，各通知有独立已读状态。时间型默认提前24小时和1小时，最多3个偏移；日期型在用户选定日内时刻提醒；未知时间不提醒。

- AC-01：重复执行同提醒100次最多一条通知。完成、取消、删除或改期后，旧版本提醒不再生成通知；已发生通知与未来提醒分开。
- AC-02：正常运行到期后≤60秒在服务端生成通知；浏览器30秒轮询存在额外显示延迟，关闭浏览器不承诺设备弹窗。
- AC-03：恢复时近24小时到期提醒补发且标延迟，更早仅逾期展示；对最多500条ACTIVE记录修改提醒偏好，重新查看时应全部采用新偏好或全部保留旧偏好，不出现一部分新、一部分旧。关联TC-22至TC-26。

### 6.15 FR-15 增强检索与历史浏览

**优先级：低。来源：SRC-U01、SRC-U04、SRC-D01、SRC-U06。** 用户可组合标题、群来源、状态、日期筛选本人条目，并从结果便捷浏览提取方式、来源和修改历史。检索结果分批显示；默认每批20条、最多100条。基本条目查看、确认时证据、改期前后值及原文清理标识仍由FR-09、FR-11、FR-12、FR-17保证，不因本项下调而取消。

- AC-01：准备两个用户、两个同名群及跨日期/状态条目，单条件及组合检索返回准确的本人结果；无匹配明确为空，不能混入他人内容。
- AC-02：从检索结果可进入同一条目的初始/改期/取消来源及历史；已清理原文仍只显示清理标识。关闭增强检索后，条目详情的基本来源与变更查看仍可用。关联TC-19、TC-27、TC-29。

### 6.16 FR-16 模式、调用额度与成本可见性

**优先级：高。来源：SRC-U02、SRC-T02、SRC-D01。** 用户可选RULE_ONLY/MODEL_AUTO及每日请求额度，默认100、可设0、最高200。展示派发/实际请求记录、token（有返回时）、未知用量及回退原因。请求次数上限不等于货币支出硬上限。

- AC-01：并发竞争最后1次额度不超额；首次、重试和探测全部计入额度；未知用量不能写成0费用。
- AC-02：关闭模型后未派发请求转规则；已派发不可撤回，页面明确边界；默认规则任务不因后来开启模型而被自动改成付费路径。关联TC-10/11/16/34。

### 6.17 FR-17 内容清理与保留

**优先级：高。来源：SRC-U04、SRC-D01。** 用户可清理来源内容并删除个人条目；正文/候选复制文本最多30天，待确认候选14天、去重元数据90天、站内通知90天，备份7份。

- AC-01：清理正文同时清除证据、提案复制文本及目标提示；运行中提取失效，迟到模型结果不能写回；已确认个人记录独立保留。
- AC-02：90天后来源骨架不破坏历史关联，去重身份结束保留；备份7天内滚动淘汰。界面说明在线删除不等于立即删除所有历史备份。关联TC-22/27/28/33。

### 6.18 FR-18 脱敏运维与接入状态

**优先级：中（维护操作）；低（详细指标展示）。来源：SRC-U04、SRC-T01、SRC-D01、SRC-U06。** OPS可维护授权群、查看连接、队列、模型与备份结果及脱敏错误，暂停异常接入。详细指标统计为低优先级。FR-01的权限隔离、FR-03的基本断线/受限状态、FR-17的保留与NFR-09的恢复不依赖增强维护台。

- AC-01（中）：分别模拟断线、授权错误、模型故障、存储不可用，应显示可区别的影响与处置提示；有心跳不能替代全量模式验收。禁用群后未完成提取停止生效。
- AC-02（中；隔离约束为高）：OPS无个人资源权限，诊断不含敏感正文。直接访问个人资源及触发含敏感正文的失败输入，均不得泄露。关联TC-01、TC-29、TC-32、TC-33。
- AC-03（低）：维护台可进一步显示队列长度/最老等待、模型尝试/回退数、最近备份时间及结果；以已知计数替身核对显示，缺指标标未知。对应HMI-06、设计UI-07及TC-34。

## 7 非功能需求与验证条件

所有数值为验收目标，尚未达到的不能写成现状。高优先级用于核心可用性、风险控制及运行上限，中优先级用于可维护和基本可操作性，低优先级用于可延后体验优化。7.3给出规划依据与适用负载，7.4给出质量及易用性目标的取舍；这些依据不等于实测。

### 7.1 提取质量口径

冻结集包含60段规则支持范围通知、40段自由表达/明确改期通知、20段无关/否定/歧义文本。人工标注事项、动作、类型、时间精度、证据；缺上下文样例的正确结果可为UNKNOWN_TARGET，不能要求模型猜前文。

规则验收使用“60段支持范围通知＋公共20段”，模型增强验收使用“40段自由表达通知＋公共20段”；公共20段须逐条标明“应无候选”“应保留未知候选”或具体动作，不能把所有否定句一律当作无事项。公共样例计入各自TP/FP/FN；无事项样例多出候选计FP，应保留未知的事项被漏掉计FN。模型测试未获得有效MODEL输出的事项计FN并报告回退数，不从分母删除，也不把RULE回退结果算作模型成功。

精确率=TP/(TP+FP)，召回率=TP/(TP+FN)；事项匹配要求动作、类型和核心任务一致。分母为0标不可评价，不算100%。日期归一化正确率以有明确日期的已匹配事项为分母，同时必须报告漏提数。另报告“带明确日期事项端到端恢复率=正确恢复事项及日期的数量/标注的带明确日期事项总数”，防止遗漏困难样例后指标虚高。该诊断指标不另设未经验证的新门槛。

歧义样例编造精确时刻计失败；标题正确但DDL错仍记录时间错误。样例、标注规范、提示词版本、模型型号、运行日期与token消耗固定记录；冻结后不能删失败样例。未达到目标时调整实现或显式修订基线，不改变统计分母掩盖不足。

### 7.2 模型时延与提醒时延口径

在7.3规定负载内，等待模型执行机会最多30秒，超过即转规则并显示“模型繁忙回退”；取得执行机会后，每次等待供应商响应最多30秒，最多追加一次重试（也计额度）。供应商慢、断流或无有效结果时停止等待，规则可用则回退，规则也失败则显示明确失败终态，不无限转圈。

90秒是本地执行过程到候选/规则结果/明确失败的P95目标，不是模型成功率或供应商SLA；规划分配为最多两次响应等待60秒、退避合计≤5秒、规则处理目标5秒及本地校验/调度余量20秒。若本地执行已到90秒仍无可用结果，应结束为明确失败，并提供手动录入或重新导入入口；超时后的供应商结果不得再生成第二套候选。初次执行机会等待上限为30秒；追加尝试仍须在原90秒执行预算内，无法取得机会则转规则，不重新开启一段90秒。上述期限须用慢响应、断流、坏输出及规则失败替身验证，真实云模型的成功率、时延和费用另测。

并发≤2与30秒占位只约束HUSTIME客户端尚未完成/超时的活动请求。本地超时结束等待不证明供应商停止处理，实际用量可能未知或继续计费；迟到结果丢弃，用量按FR-16如实显示。不能用本地并发上限宣称供应商后台同时计算也≤2。

分别报告等待模型机会时长、执行时长、接收至终态总耗时的P50/P95/最大值和超时数。30＋90＝120秒只表示该路径的等待与执行期限预算，**不是两个P95相加得到的总P95保证**；负载超过7.3峰值、服务器停机及等待恢复须另报。普通规则路径仍按NFR-01判定。

提醒≤60秒指正常运行时服务端持久化站内通知；浏览器每30秒轮询另有延迟。外部服务不可用、浏览器关闭和服务器停机分别说明，不能把“已生成”“已展示”“用户已读”混为一谈。

### 7.3 容量、峰值与性能目标的推导依据

本节是课程原型的规划计算（来源SRC-D01、SRC-U06），**不是校园调查、压测结果或供应商性能承诺**。上线后须测量消息分布、模型分支占比、尝试次数和服务时长再校准；超出假设时按FR-06、FR-16、NFR-08回退或背压，不擅自提高费用额度。

敏感性检查：p升至10%时约2,200次尝试/日、平均需1.53并发，虽低于2，突发仍超载；p升至100%时约22,000次尝试/日，既超过合计预算，也远超两槽能力，必须大量规则回退。若每项都追加一次，5%场景变为2,000次尝试/日；次数、占位与费用都不能继续按1,100计算。服务变快可降低占位，不能据此放宽未经测量的容量保证。

20,000消息/10,000候选/5,000条目的性能背景集仅用于可重复比较；容量验收另覆盖20账号共10,000条ACTIVE上限、30天最多600,000个正文处理单元以及4,000字符极值。磁盘容量应依据实际平均正文长度、索引与7份备份核算，记录空闲空间与保留清理结果；单日测试通过不能证明30天可容纳。若容量不足，部署扩容或限制接入并告警，不静默缩短承诺保留期。

### 7.4 质量门槛与定性易用性验证的依据

规则限定明确语法，故精确率目标95%高于自由表达模型的90%；两者召回率均至少85%，防止以大量弃答换取好看的精确率。明确日期归一化至少95%是减少错期的工程门槛，日期端到端恢复率另报；确认前零落历、未知不编造是阻断项。门槛反映错误后果与个人核对成本的取舍，不来自尚未进行的统计实验。例如恰有60个标注事项时，85%召回至少检出51个；实际验收按事项数及TP/FP/FN计算，不把文本段数直接当事项数。

120段冻结集是分层的工程验收与回归集合，覆盖明确语法、自由表达及无关/否定/歧义，不能据此推断真实QQ群总体质量或5%的模型分支占比。须保留各子类结果、样本/事项数、原始计数和失败样例；小分母时报告原始数量，不以百分比掩盖不确定性。标注由提交者逐项完成并复核，冻结前记录规则及争议项；当前尚无已完成标注或运行结果。

5名目标学生试用明确为**形成性、定性验证**，用于发现字段理解、未知时间、相关性判断与错误恢复的障碍。统一提供“导入一条通知—核对日期与相关性—加入个人日程”任务；逐人记录耗时、独立完成情况、卡点、所用视口及访谈反馈，停止计时时点为成功看到条目。少于4人无指导在2分钟内完成触发交互整改与复测，“4/5”不是总体成功率或显著性结论。桌面/移动可操作、键盘核对、错误定位属于可客观检查的中优先级要求；两分钟速度优化为低优先级。后续若要推断群体易用性，应另定目标总体、抽样方式、置信精度和样本量，不把本次5人观察充作统计证据。

## 10 优先级与合理性

### 10.1 使用频率×错误后果二维表

频率F：3＝预计每日多次，2＝每周数次，1＝偶发/故障时。后果C：3＝越权、错期/误取消、数据损失、失控付费或核心闭环失效；2＝可恢复返工或信息查找受阻；1＝轻微不便且有完整替代路径。两维均为场景推断，尚无真实频率调查。记录分数F×C以便复核，不把它当精确的风险概率。

| 使用频率F＼错误后果C | C＝1 轻微不便 | C＝2 可恢复返工 | C＝3 关键损害 |
| --- | --- | --- | --- |
| F＝3 每日多次 | 3分／低：周日历视觉布局有列表替代 | 6分／中：基本列表、冲突提示、键盘与字段定位 | 9分／高：确认、时间正确性、个人隔离 |
| F＝2 每周数次 | 2分／低：组合筛选、两分钟流畅性优化 | 4分／中：维护扩展、常规运维操作 | 6分／高：改期/取消、额度设置 |
| F＝1 偶发/故障时 | 1分／低：群别名编辑、详细指标展示 | 2分／中：接入配置与可恢复操作 | 3分／高：备份恢复、清理防迟到写回、无敏感信息泄露 |

判定顺序：C＝3或核心闭环必需项始终为高；C＝2为中；C＝1且有替代路径为低。乘积分数只在同档排序，不能以低频×低分把备份或授权降档。核心依赖（如通知接入、规则回退）即使交互频率不高，也按闭环失效归入C＝3。
